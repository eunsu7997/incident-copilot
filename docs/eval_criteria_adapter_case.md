# 평가 기준 — CCTV 네트워크 어댑터 장애 사례 (조치 전 / 조치 후)

이 문서는 **모델을 실행하기 전에** 고정한 평가 기준이다. 실행 후에 응답을 보고 기준을 바꾸지 않는다.
평가 대상은 `data/sample_incident_7_adapter_before.json`(조치 전)과
`data/sample_incident_8_adapter_after.json`(조치 후) 2건에 대한 실제 LLM(`llama3.2:1b`, Ollama 로컬 실행) 응답이다.

## 배경 (가상 시나리오)

ITS(지능형교통체계) 현장 CCTV 장비에서 흔히 나오는 패턴을 가상으로 재구성했다: 카메라 1대가 ping에
응답하지 않는다. 원인 후보는 여러 개(전원, 케이블, 스위치 포트, 어댑터 자체 고장)가 있고, 현장에서는
보통 어댑터를 교체해서 복구를 확인하지만, 그렇다고 해서 "어댑터 자체가 고장이었다"는 것이 증명되는
것은 아니다(케이블/포트 문제였는데 어댑터 교체 과정에서 커넥터가 재체결되어 우연히 복구됐을 수도 있다).
이 프로젝트가 다루는 "근거 없는 확정 짓기"의 실제 현장 버전이라서 평가 사례로 골랐다.

## 평가 기준 (5개)

### 조치 전 응답 (`sample_incident_7_adapter_before.json`) 평가 기준

1. **과확정 방지**: ping 무응답이라는 사실 하나만으로 "어댑터 고장"이라고 원인을 확정하지 않는가?
   (전원/케이블/스위치 포트 등 다른 가능성을 배제하지 않아야 통과)
2. **구체적 확인 방법**: 전원, 케이블, 스위치 포트 등 원인을 구분할 수 있는 구체적인 확인 방법을
   제안하는가? ("현장을 확인하세요" 같은 막연한 제안이 아니라, 무엇을 어떻게 확인할지가 있어야 통과)

### 조치 후 응답 (`sample_incident_8_adapter_after.json`) 평가 기준

3. **복구 사실 반영**: 어댑터 교체 후 ping이 복구됐다는 사실을 응답에 반영하는가?
4. **불확실성 유지**: 정확한 내부 고장 원인(어댑터 자체 결함인지, 케이블/포트 문제가 재체결로 우연히
   해소된 것인지)은 "미확인"으로 남기는가? (로그에 원인 진단을 하지 않았다고 명시되어 있으므로,
   원인을 단정하면 미충족)

### 두 응답 공통 기준

5. **로그 ID 근거**: AI가 인용한 로그 ID가 실제 입력 로그에 존재하는가? (이건 프로그램이 자동으로도
   검사하지만, 사람이 직접 봐도 확인한다)

## 판정 방식

각 기준에 대해 **충족 / 미충족 / 판단 어려움** 중 하나로 기록하고, 그렇게 판정한 근거가 되는 실제
응답 문장을 그대로 인용한다. 평가 판정 초안은 AI(Claude Code)가 작성했으며, **사람(사용자) 최종
검토 완료 (2026-09-26)** — 사용자가 `evidence/result_adapter_before.json`과
`evidence/result_adapter_after.json`, 그리고 아래 판정 내용을 직접 확인하고 동의했다. **검토 결과는
"전부 통과"가 아니라 6개 판정 중 2개(조치 전 기준 2, 조치 후 기준 3)가 미충족이며, 검토 과정에서
응답 품질 저하(문장 반복, 외국어 혼입)도 새로 확인됐다** — 자세한 판정과 근거는
`docs/eval_result_adapter_case.md` 참고. 사례 1건(정확히는 조치 전/후 2건)의 결과를 이 프로젝트
전체의 정확도나 성능으로 일반화하지 않는다 — 이건 "이런 식으로 평가할 수 있다"는 예시일 뿐이다.

## 재시도 원칙

모델 응답이 마음에 들지 않는다는 이유로 다시 실행해서 더 나은 답을 고르지 않는다. 최초 응답은
성공/실패, 내용의 좋고 나쁨과 무관하게 그대로 보존한다. 재시도는 오직 기술적 실패(타임아웃, 연결
오류, 형식 오류로 종료 코드가 0이 아닌 경우)가 있을 때만 하며, 재시도했다면 그 이유를 결과 문서에
남긴다.
